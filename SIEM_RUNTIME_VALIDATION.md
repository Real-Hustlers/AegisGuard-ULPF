# SIEM runtime validation

## Scope

This validation ran ULPF-generated Windows Security OCSF events through the
existing public `Real-Hustlers/AegisGuard` SIEM at commit
`653dec2afcfd92951888b3c2a1eaf05456493b28`. The SIEM source was cloned to a
temporary workspace only; no SIEM source files were changed.

The ULPF-side addition used for the actual SIEM ingestion boundary is
`translate_ocsf_jsonl_to_siem_ingestion_envelope()` in
`src/aegisguard_ulpf/integration/siem_contract_mapper.py`. It produces the
machine envelope consumed by the SIEM's `import_merge.py` workflow.

## Commands executed

```text
git clone --depth 1 https://github.com/Real-Hustlers/AegisGuard.git .siem-runtime-validation

python -c "... JsonlOutputWriter(...).write_ocsf(map_windows_security_event_to_ocsf(...)) ..."
python -c "... translate_ocsf_jsonl_to_siem_ingestion_envelope(...) ..."

python -c "from backend.analyzer.ingestion import import_merge; ...; import_merge.merge_logs()"
python -c "from backend.analyzer.ingestion.classifier import classify_logs; classify_logs(...)"
python -c "from backend.analyzer.ingestion.correlation_engine import run_correlation; run_correlation()"
python -c "from mysql.merge_log_sql import import_classified_logs_to_db; import_classified_logs_to_db(...)"
python -c "from backend.analyzer.service import get_dashboard_summary, get_events; ..."
```

The SIEM runtime commands used the available system Python because the ULPF
virtual environment does not contain the SIEM's `joblib` and `pandas`
dependencies.

## Input and output samples

The input contained three Windows Event ID 4625 failures, one Event ID 4624
success, and one Event ID 4688 process creation. All events used host
`ULPF-RUNTIME-01`; the failures and success used user `runtime-user` and
source IP `10.0.0.5`.

The first merged SIEM record generated by `import_merge.py` was:

```json
{
  "log_id": "LOG-000001",
  "machine_id": "ULPF-RUNTIME-01",
  "hostname": "ULPF-RUNTIME-01",
  "os": "Windows 11",
  "timestamp": "2026-09-01T10:00:00Z",
  "event_type": "FAILED_LOGIN",
  "user": "runtime-user",
  "source_ip": "10.0.0.5",
  "process": "",
  "severity": "LOW"
}
```

The classifier processed all five records with these event types:

```text
FAILED_LOGIN, FAILED_LOGIN, FAILED_LOGIN, SUCCESSFUL_LOGIN, PROCESS_CREATED
```

Correlation generated:

```text
Multiple Failed Login Attempts (HIGH)
Possible Brute Force Attack (CRITICAL)
```

After the SIEM's existing `import_classified_logs_to_db()` step, the dashboard
service returned `events: 5`, `devices: 1`, and five event rows.

## Validation result

| Check | Result |
| --- | --- |
| Old SIEM can receive ULPF-generated input | Pass, through the ULPF machine-envelope translator. |
| `import_merge.py` processes the envelope | Pass: one machine file, five merged logs. |
| `classifier.py` consumes and classifies events | Pass: five classified logs. |
| `correlation_engine.py` consumes them | Pass: two incidents and a response JSON file. |
| Dashboard data is generated | Pass after the SIEM's existing classified-log SQLite import step. |

## Blockers and constraints

- A post-merge `merged_logs.json` is not input to `import_merge.py`; that
  module reads per-machine envelope files. The ULPF envelope translator closes
  this ULPF-side gap without changing the SIEM.
- `import_merge.py` intentionally projects events to its fixed schema and
  therefore drops additive ULPF fields such as `ulpf_original_event`. The
  direct merged-log translator retains those fields; the SIEM ingestion route
  cannot retain them without an SIEM change, which was not made.
- The ULPF virtual environment lacks the SIEM's `joblib` and `pandas`
  dependencies. The system Python already had them, so this did not block the
  runtime validation.
